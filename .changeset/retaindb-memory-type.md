RetainDB Server no longer refuses memories for their type, and its legacy endpoint stores them before answering. The Provider sent the Memory Spaces category as RetainDB's memory type, and RetainDB Server answers a type outside its list with HTTP 400: its `POST /v1/memory` takes `preference` and `decision` but not `fact`, `insight`, `context` or `general`, so every memory of those categories was refused, the default `general` and the `context` that Runtime and document archives use included, and its legacy `POST /v1/memories` refused all six categories. Those four categories are now sent as `factual`, the type RetainDB falls back to itself, and the legacy endpoint receives `factual` for every category. That endpoint also queued every write while the Provider reported it stored; it is now asked to store the memory before it answers, a server that queues the write anyway is reported as queued rather than stored, and a stored receipt from RetainDB Server carries the memory's id. Reading back, a memory RetainDB returns as `preference` or `decision` gets that category, from lists and from RetainDB Local's search alike, and any other type reads as `general`. RetainDB Local, which infers types itself, stores the same types as before.
