# OpenViking 记忆空间的精确文本关键词检索：issue #452

[English](./README.md) | [Issue #452](https://github.com/omdsh-dev/dsh-mnemon/issues/452) | [验证记录](./verification.json)

Issue #452 指出：OpenViking 记忆空间只能按语义检索，因此精确的编号、版本号、路径或错误码查找得不稳定，或者排在相近条目之后。而 OpenViking 本身就有精确文本接口 `POST /api/v1/search/grep`。

基线为 main `a7e3bc54`。首轮验证于 2026-10-23 进行，评审后的复测于 2026-10-24 进行（Asia/Shanghai），环境如下：

- macOS arm64，Node 24.19.0，pnpm 10.13.1；
- OpenViking v0.4.21：取自 Docker 镜像，API Key 认证；
- OpenViking 0.5.1.1：取自 PyPI，运行在 Python 3.12.13 上，dev 认证模式。

两台服务端都只监听本机回环地址，使用 `text-embedding-ada-002` 向量（1,536 维），并在 `viking://user/wp452/memories` 下存放同样的 64 条合成记录：

- 一条 PostgreSQL 安装路径与服务名；
- 一条 Redis 记录、一条笔记本上的 Docker 记录；
- 一条带 SHA-256 的档案归档索引；
- 60 台只有数字不同的主机 `fleet-000` 至 `fleet-059`（`Docker Engine 29.8.<n>`）。

评审补充了第二组数据，v0.4.21 上存放在 `viking://user/rv460/memories`，0.5.1.1 上存放在 `viking://user/wp452atlas/memories`：

- 六条各 50 行的 “Atlas sprint log” 记录，写着 “Atlas” 的行比一次 grep 能返回的还多；
- 最新的一条 “Atlas rollout: fleet-777 was upgraded to Docker Engine 29.9.1”；
- 含 `v5.2.2` 与 `Python3.12` 的记录、中文与俄文句子，以及一份带 SHA-256 的文档。

0.5.1.1 上的第三个空间 `viking://user/wp452big/memories` 存放 512 条单行记录，用于测量开销。0.5.1.1 不接受 Provider 写入请求中的 `timeout` 字段（#455），会拒绝 Provider 自己的写入，所以 0.5.1.1 上的这几组数据直接经 `content/write` 写入，文件名与 Provider 生成的一致。

## 原因

无论 `mode` 是什么，Provider 都把检索发往语义接口 `search/find`。所以直接检索里的**关键词检索**，以及 `mode: "keyword"` 的 `mnemon_recall`，实际也按语义检索。在只有数字不同的记录之间，向量分不清 `29.8.37` 与 `29.8.36`。

## 修复

OpenViking 空间的关键词检索改走 `search/grep`：

- **请求。** 先用一次 `search/grep` 把全部词（最多 8 个）作为并列选项一起查。一次 grep 最多返回 256 行匹配，并按文件名顺序遍历文件；这次 grep 装满时，再为每个词各执行一次，常见词因此不会占满稀有词需要的行数。每个请求都只发送 `uri`（该空间的记忆根）、`pattern`（转义了正则字符的查询词）、`case_insensitive` 与 `node_limit: 256`，这四个字段从 0.4.16 到 0.5.2 的每个版本都有声明。
- **拆词。** 查询按空白拆分。用直引号或弯引号括起的短语算一个词，grep 只在同一行内找到它。词尾表示句子结束的标点会去掉，所以 `fleet-777?` 查的是 `fleet-777`。`a`、`5` 这样的单字符词只在查询没有其他词时才计入；单个汉字或日文字符总是计入。
- **匹配。** 按字面、忽略大小写匹配，但不从数字或单词的中间匹配：数字不能紧挨数字，以空格分词的文字中字母不能紧挨字母。
  - `29.8.5` 不会匹配 `29.8.50`，`fleet-04` 不会匹配 `fleet-042`，`кот` 不会匹配 `который`。
  - `5.2.2` 能匹配 `v5.2.2`，`3.12` 能匹配 `Python3.12`。
  - 中文这样不以空格分词的文字可在任意位置匹配，`API` 也能在 `调用API接口` 中匹配。
  - 同时含数字和字母、至少 7 位的十六进制 ID 按开头匹配：较短的提交哈希或镜像摘要能找到完整的那个，但不会从更长 ID 的中间匹配。

  这项判断由 Provider 完成：对任何一次 grep 返回的每一行，逐个检查全部查询词。发给服务器的是不带边界条件的普通词，因为远程向量后端会把 pattern 当作词语做关键词召回。
- **排序。** 包含更稀有的词、包含的词更多的记忆排在前面：每个词的权重取决于命中的记忆中有多少条包含它，越少越重，与 BM25 的逆文档频率相同。包含相同词的记忆中，按文件名里的时间，Mnemon 最后写入的排在前面，因此更新排在被它取代的记忆之前。文件名不带这个时间的文件（例如 OpenViking 自己写入的）按 grep 的顺序排在其后。记忆根以外的文件和 OpenViking 的系统文件（`.abstract.md`、`.overview.md`）会被排除。
- **结果内容。** 与语义检索一样读回完整记忆，结果不带分数。
- **提示。** 第八个词之后的词没有查询、某个词装满了它自己的 grep（此后的记忆可能缺失）、命中的文件读不到时，结果都会说明。
- **特殊情况。** 尚未写入任何记忆的空间（记忆根还不存在）返回空结果。没有 `search/grep` 的服务器（返回不指明资源的 404 或返回 405）改用语义检索作答，并在提示中说明；其他 grep 错误会如实报告。
- **不变的部分。** 智能召回、基础匹配以及未指定模式的检索，仍与以前完全一样走语义检索。

以**关键词检索**策略使用 **Agent 查询**时，会执行同样的检索并把结果交给任务 Agent，因此它现在根据精确文本的匹配作答。

档案归档在复用上次尝试留下的索引时，也会以关键词模式按内容哈希查找空间。在 OpenViking 上，这一查找现在是精确的：哈希按原文命中，归档在复用前仍会核对内容。Host 测试与 e2e 环境使用的协议 fixture，现在也像 OpenViking 一样应答 `search/grep`：按文件名顺序遍历，最多返回 `node_limit` 行。

## 结果

### 逐个版本检索

对全部 60 台主机，以关键词模式检索 `29.8.<n>`，上限 10 条：

| 服务器 | main：精确主机排第一 | main：进入前 10 | main：未找到 | main：每次结果数 | 修复：精确主机排第一 | 修复：每次结果数 |
|---|---:|---:|---:|---:|---:|---:|
| v0.4.21 | 60 次中 34 次 | 56 | 4 | 10 | 60 次中 60 次 | 1.02 |
| 0.5.1.1 | 60 次中 34 次 | 56 | 4 | 9.03 | 60 次中 60 次 | 1.02 |

修复后多出的 0.02 来自 `29.8.0`：笔记本那条记录也写着这个版本。每次检索的平均耗时：main 为 942 ms 与 901 ms，修复后为 13 ms 与 12 ms。

### 经记忆空间 Source 的直接检索

经 Source 以关键词检索查询 `29.8.37`：

- main 返回 10 条，全部判为 `high`，精确的主机排第三；
- 修复后只返回这台主机。

智能召回在修复前后返回同样的 10 条。

### 开销随空间大小的变化

查询词都匹配不到任何内容，因此 grep 要读完每个文件；只有 `shard` 例外，512 条记录都含有它。时间为经 Provider 执行 7 次关键词检索的中位数：

| 服务器 | 记忆条数 | 一个词 | 八个词 | `shard q-0137` | `shard` 加七个词 |
|---|---:|---:|---:|---:|---:|
| 0.5.1.1 | 11 | 4 ms | 4 ms | | |
| 0.5.1.1 | 64 | 9 ms | 9 ms | | |
| 0.5.1.1 | 512 | 47 ms | 47 ms | 113 ms | 402 ms |
| v0.4.21 | 16 | 6 ms | 5 ms | | |
| v0.4.21 | 64 | 9 ms | 9 ms | | |

匹配不到内容的 grep 会读完记忆根下的每个文件：两台服务器上的 `files_scanned` 都等于记忆条数。在 0.5.1.1 上，一次 grep 每条记忆约需 0.09 ms；这个版本会用 Python 读取每个文件，先去掉其中的 `MEMORY_FIELDS` 元数据再匹配。只要合并的 grep 没有装满，八个词的开销与一个词相同。常见词会把它装满，之后每个词各执行一次 grep：`shard` 那次读到第 256 条就停下，每个稀有词那次都要读完全部文件，这就是八个词的 402 ms。各次耗时加起来，相当于服务器逐个执行同一次检索的各个 grep，尽管 Provider 是同时发出的。

## 限制

- **有多少结果能送到模型。** 结果不带分数。在 #461 合并之前，召回质量策略把它们算作 `unknown` 相关度：默认的 `strict-v1` 每次检索最多保留两条，模型召回每次尝试只放行一条。唯一的编号或版本号只需要一条，但许多记忆都含有的词会在这里被截断（#454）。#461 把分数未经校准的 Provider（包括 OpenViking）返回的条目按联合检索中的位置排序（层级 `ranked`）；评审在本地合并两个分支后确认，这些条目届时会以 `ranked` 送达。#461 应先于本修改合并，或与之一起合并。
- **常见词。** 每次 grep 最多返回 256 行，对 Mnemon 写入的文件从旧到新遍历，因此只含某个常见词的较新记忆可能缺失。结果会指出这个词，换用更稀有的词即可找到。
- **开销。** grep 装满之前会读取每个记忆文件，0.5.1.1 还用 Python 读取并先去掉其中的元数据，因此空间越大，关键词检索越慢：在 0.5.1.1 上每条记忆每次 grep 约 0.09 ms；常见词与另外七个词同查时，最多执行九次 grep。
- **没有录制 WebUI。** 直接检索页面本身没有变化，上面经 Source 的运行调用的是页面所用的同一个 `search` 操作。
